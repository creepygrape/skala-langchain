# 맞춤형 콘서트 예매 가이드 — 요구사항 명세서

## 1. 프로젝트 개요

### 1.1 프로젝트명

**맞춤형 콘서트 예매 가이드**

### 1.2 목적

콘서트 예매 페이지에는 공연 일정, 팬클럽 인증, 선예매, 일반예매, 티켓 수령, 본인 확인, 취소/환불 등 많은 정보가 한 페이지에 섞여 있다.

사용자는 전체 공지를 직접 읽으며 자신에게 필요한 정보를 찾아야 하고, 중요한 정보가 본문뿐 아니라 상세 이미지에 포함되는 경우도 있어 필요한 내용을 놓치기 쉽다.

본 서비스는 사용자가 **콘서트 예매 페이지 URL과 자신의 상황을 자연어로 입력하면**, 해당 사용자에게 필요한 예매 정보만 찾아 정리해주는 AI 도우미를 제공한다.

---

## 2. 문제 정의

### 2.1 해결하려는 불편

콘서트 관람객은 예매 페이지 전체를 읽으면서 다음과 같은 정보를 직접 찾아야 한다.

- 팬클럽 인증 대상인지
- 선예매 또는 일반예매 일정이 언제인지
- 회차별 구매 가능 매수가 몇 장인지
- 티켓을 배송받는지 현장에서 수령하는지
- 본인 확인을 위해 무엇을 준비해야 하는지
- 예매 또는 취소 가능 시간이 언제까지인지
- 자신에게 적용되는 별도 주의사항이 있는지

공지 내용이 여러 영역에 흩어져 있고 대상별 조건과 예외가 존재하기 때문에 필요한 정보만 빠르게 파악하기 어렵다.

### 2.2 왜 LLM이 필요한가

단순 키워드 검색만으로는 사용자의 자연어 조건과 여러 문단에 흩어진 예매 규정을 함께 해석하기 어렵다.

예를 들어 사용자가 다음과 같이 질문할 수 있다.

> 팬클럽 선예매 할 거고 첫날 공연 갈 건데 현장수령이면 내가 언제 뭘 해야 해?

이 질문에는 다음 조건이 동시에 포함된다.

- 팬클럽 회원
- 선예매 이용
- 특정 공연 회차
- 현장수령

LLM은 이러한 자연어 조건을 이해하고, 관련 공지 내용을 종합하여 사용자의 상황에 맞는 안내를 생성하는 역할을 담당한다.

---

## 3. 대상 사용자

콘서트 예매 공지를 읽을 때 자신에게 필요한 정보를 빠르게 확인하고 싶은 관람객.

로그인 또는 사용자 계정 기능은 제공하지 않는다.

---

## 4. MVP 지원 범위

### 4.1 지원 사이트

MVP에서는 **NOL Ticket의 콘서트 상품 상세 페이지**만 지원한다.

예시 URL:

https://nol.yanolja.com/ticket/products/26012624

다른 예매 사이트를 범용적으로 지원하지 않는다.

### 4.2 필수 입력

1. **예매 페이지 URL**
2. **사용자 질문 또는 상황**

질문은 자유로운 자연어 문장으로 입력한다.

예시:

- 팬클럽 선예매인데 언제부터 예매할 수 있어?
- 일반예매로 갈 건데 꼭 준비해야 하는 게 뭐야?
- 티켓 현장수령 예정인데 신분증이 필요한가?
- 첫날 공연을 예매하려는데 언제까지 예매할 수 있어?
- 티켓 배송은 언제 시작해?
- 취소하면 수수료가 얼마나 발생해?

별도의 복잡한 체크박스 입력을 필수로 요구하지 않는다.

---

## 5. 핵심 사용자 흐름

~~~text
1. 사용자가 NOL Ticket 콘서트 상품 URL 입력
2. 시스템이 예매 페이지의 HTML 텍스트 수집
3. 상세 공지 이미지가 존재하면 이미지 내용을 텍스트화
4. HTML 텍스트와 이미지 텍스트를 LangChain Document로 통합
5. Document를 검색 가능한 단위로 분할
6. Embedding 후 Vector Store에 저장
7. 사용자가 자신의 상황 또는 질문 입력
8. 사용자 질문의 의도와 필요한 정보 주제를 분석
9. Retriever가 질문과 관련 있는 공지 Context 검색
10. 검색된 Context와 사용자 질문을 LLM에 전달
11. LLM이 사용자의 상황에 맞는 예매 정보를 생성
12. Structured Output 형태로 사용자에게 제공
~~~

## 6. 기능 요구사항

### FR-001. 예매 URL 입력 및 검증

사용자는 NOL Ticket 공연 상품 URL을 입력할 수 있어야 한다.

#### 정상 조건

유효한 NOL Ticket 상품 페이지인 경우 분석을 시작한다.

#### 오류 조건

다음의 경우 사용자에게 오류를 안내한다.

- URL 형식이 올바르지 않음
- NOL Ticket 상품 페이지가 아님
- 페이지 접근 실패
- 페이지에서 공연 정보를 가져올 수 없음

---

### FR-002. HTML 텍스트 수집

시스템은 입력받은 예매 페이지에서 HTML로 제공되는 텍스트를 수집해야 한다.

수집 대상 예시는 다음과 같다.

- 공연명
- 공연 장소
- 공연 기간
- 공연 시간
- 티켓 가격
- 예매 가능 시간
- 티켓 배송 정보
- 취소/환불 정보
- 기타 HTML 형태의 안내사항

수집 결과는 LangChain에서 사용할 수 있는 Document 형태로 변환한다.

---

### FR-003. 상세 이미지 탐지

시스템은 예매 페이지에서 상품 상세 안내 이미지가 존재하는지 확인해야 한다.

이미지가 여러 개 존재할 경우 상세 공지와 관련된 이미지를 수집할 수 있어야 한다.

---

### FR-004. 상세 이미지 텍스트 추출

상세 이미지에 포함된 안내문을 OCR 또는 Vision 모델을 이용하여 텍스트로 변환해야 한다.

추출 대상 예시는 다음과 같다.

- 팬클럽 인증 일정
- 선예매 일정
- 일반예매 일정
- 매수 제한
- 본인 확인 안내
- 티켓 수령 안내
- 공연 입장 안내
- 기타 예매 주의사항

이미지 분석에 실패한 경우 전체 서비스가 중단되지 않아야 한다.

HTML에서 수집된 정보만 사용하여 가능한 범위의 결과를 제공하고, 사용자에게 이미지 정보가 누락되었음을 알린다.

---

### FR-005. Document 통합 및 Metadata 관리

HTML에서 가져온 텍스트와 이미지에서 추출한 텍스트를 하나의 검색 대상 Document 집합으로 관리한다.

각 Document에는 최소 다음 metadata를 포함한다.

~~~json
{
  "source_type": "html | image",
  "source_url": "원본 URL",
  "section": "문서 영역"
}
~~~

---

### FR-006. Document 분할

긴 공지 문서는 검색하기 적절한 크기로 분할한다.

분할 시 가능한 한 하나의 규칙이나 안내 내용이 여러 Chunk로 불필요하게 분리되지 않도록 한다.

예를 들어 아래 내용은 가능하면 동일하거나 인접한 Context로 유지한다.

~~~text
팬클럽 인증 안내
- 인증 기간
- 인증 대상
- 인증 방법
- 주의사항
~~~

---

### FR-007. Vector Store 저장

분할된 Document를 Embedding하여 Vector Store에 저장한다.

목적은 전체 예매 공지를 매번 LLM에게 전달하지 않고, 사용자 질문과 관련 있는 내용만 검색하는 것이다.

MVP에서는 NOL Ticket 상품 ID를 공연 식별자인 `concert_id`로 사용한다.

Vector Store에 여러 공연의 Document가 존재할 수 있으며, 질문 처리 시 사용자가 입력한 URL의 `concert_id`에 해당하는 Document만 검색한다.

이미 분석한 공연 URL이 다시 입력된 경우 기존 Vector Store 데이터를 재사용하여 HTML 수집, OCR, Embedding을 반복하지 않는다.

MVP에서 Vector Store의 영구 저장은 필수가 아니다.

---

### FR-008. 사용자 질문 입력

사용자는 예매 공지와 관련된 질문을 자연어로 입력할 수 있다.

예시:

> 팬클럽 선예매 할 건데 언제 뭘 해야 해?

> 일반예매로 현장수령할 예정이야. 필요한 것만 알려줘.

> 배송받을 건데 티켓이 언제 오는지랑 취소 가능 기간 알려줘.

---

### FR-009. 사용자 질문 분석

시스템은 사용자의 자연어 질문에서 필요한 정보 주제를 구조화할 수 있어야 한다.

예시 입력:

> 팬클럽 선예매 할 거고 현장수령 예정이야.

예시 분석 결과:

~~~json
{
  "booking_type": "fanclub_presale",
  "ticket_delivery": "onsite",
  "needed_topics": [
    "fanclub_verification",
    "presale_schedule",
    "onsite_pickup",
    "identity_verification"
  ]
}
~~~

질문 분석 결과는 Retriever 검색을 보조하는 Context로 활용한다.

단, 단순 질문에 대해서는 불필요한 추가 LLM 호출을 최소화할 수 있도록 구현할 수 있다.

---

### FR-010. 관련 Context 검색

시스템은 사용자 질문 및 질문 분석 결과와 관련성이 높은 Document를 Retriever를 통해 검색해야 한다.

예를 들어 다음 질문:

> 팬클럽 선예매 언제 열려?

에는 전체 공지가 아니라 다음 내용이 우선적으로 검색되어야 한다.

- 팬클럽 인증
- 팬클럽 선예매
- 선예매 대상
- 선예매 시간
- 선예매 매수 제한

---

### FR-011. 맞춤형 답변 생성

LLM은 다음 Context를 함께 사용해 답변해야 한다.

1. 사용자의 원본 질문
2. 질문에서 파악한 사용자 조건
3. Retriever가 검색한 예매 공지

LLM 자체 지식만으로 예매 정보를 만들어서는 안 된다.

검색된 문서에 존재하지 않는 정보는 추측하지 않는다.

---

### FR-012. 구조화된 출력

최종 결과는 최소 다음 구조를 가져야 한다.

~~~json
{
  "summary": "사용자에게 가장 중요한 핵심 안내",
  "schedule": [],
  "requirements": [],
  "ticket_info": [],
  "warnings": [],
  "sources": []
}
~~~

#### summary

사용자의 질문에 대한 짧은 결론.

#### schedule

사용자와 관련된 일정.

예:

- 팬클럽 인증 기간
- 선예매 시작 시간
- 일반예매 시간
- 공연 일시

#### requirements

사용자가 준비하거나 수행해야 하는 사항.

예:

- 팬클럽 인증
- 신분증 준비
- 본인 명의 계정 확인

#### ticket_info

티켓과 관련된 정보.

예:

- 배송
- 현장수령
- 모바일 티켓
- 매수 제한

#### warnings

사용자가 놓치면 문제가 될 수 있는 사항.

예:

- 인증 기간 이후 인증 불가
- 본인확인 정보 불일치 시 입장 제한 가능

#### sources

답변 생성에 사용한 원문 근거 및 출처.

## 7. 체인 구성 요구사항

MVP는 문서 수집과 사용자 질의를 분리한다.

### 7.1 Document Ingestion Chain

공연 URL을 LLM이 검색 가능한 Context로 만드는 과정이다.

~~~text
URL
→ URL 검증
→ HTML Document Loader
→ 상세 이미지 탐지
→ OCR / Vision
→ Document 통합
→ Text Splitter
→ Embedding
→ Vector Store
~~~

URL 분석은 공연 페이지별로 한 번 수행하고, 같은 공연에 대한 여러 사용자 질문에서 Vector Store를 재사용할 수 있어야 한다.

### 7.2 Query Understanding Chain

사용자의 자연어 질문에서 예매 유형과 필요한 정보 주제를 파악한다.

~~~text
사용자 질문
→ Prompt Template
→ LLM
→ Structured Output
~~~

이 단계의 목적은 여러 의도가 섞인 질문에서 필요한 검색 주제를 명시적으로 파악하는 것이다.

### 7.3 RAG Answer Chain

질문과 관련된 공지 Context를 검색하여 최종 안내를 생성한다.

~~~text
사용자 질문
+ 질문 분석 결과
→ Retriever
→ 관련 Document
→ Prompt Template
→ LLM
→ Structured Output Parser
→ 맞춤형 예매 가이드
~~~

---

## 8. 답변 생성 규칙

LLM은 반드시 다음 규칙을 따른다.

1. Retriever가 제공한 Context를 최우선 근거로 사용한다.
2. Context에 없는 날짜, 시간, 가격, 정책을 추측하지 않는다.
3. 확인할 수 없는 내용은 "예매 페이지에서 확인할 수 없습니다."라고 답한다.
4. 사용자의 조건과 직접 관련 없는 정보는 과도하게 출력하지 않는다.
5. 날짜와 시간은 원문 정보를 임의로 변경하지 않는다.
6. 예매 성공을 보장하는 표현을 사용하지 않는다.
7. 원문과 충돌하는 안내를 생성하지 않는다.
8. 중요한 제한사항과 준비사항을 생략하지 않는다.
9. 가능한 경우 답변에 사용한 원문 근거를 함께 제공한다.

## 9. UI 요구사항

MVP UI는 단일 화면으로 구성한다.

### 입력 영역

- 예매 URL 입력창
- 사용자 질문 TextArea
- "예매 정보 확인" 버튼

### 출력 영역

- 핵심 답변
- 일정
- 준비사항
- 티켓 정보
- 주의사항
- 참고 근거

UI는 기능 검증을 우선하며 복잡한 디자인 시스템은 요구하지 않는다.

## 10. 예외 처리

### Case 1. 질문과 관련된 내용을 찾지 못함

출력:

> 예매 페이지에서 질문과 관련된 정보를 확인하지 못했습니다.

LLM이 임의로 답변하지 않는다.

### Case 2. 상세 이미지 분석 실패

HTML 분석 결과는 정상적으로 제공한다.

추가 안내:

> 상세 공지 이미지 분석에 실패해 일부 안내가 누락되었을 수 있습니다.

### Case 3. URL 접근 실패

출력:

> 예매 페이지를 불러올 수 없습니다. URL을 확인해주세요.

### Case 4. 지원하지 않는 사이트

출력:

> 현재는 NOL Ticket 상품 페이지만 지원합니다.

### Case 5. 예매와 관련 없는 질문

예:

> 오늘 저녁 뭐 먹을까?

출력:

> 입력한 공연의 예매 정보와 관련된 질문을 해주세요.

## 11. 테스트 시나리오

동일한 예매 페이지를 사용하고 사용자 질문만 변경하여 검색 Context와 최종 답변이 달라지는지 확인한다.

### Test 1. 팬클럽 선예매

입력:

> 팬클럽 선예매 할 건데 언제 뭘 해야 해?

기대 결과:

- 팬클럽 인증 관련 정보
- 선예매 날짜 및 시간
- 매수 제한
- 관련 주의사항

### Test 2. 일반예매 + 현장수령

입력:

> 일반예매로 예매하고 현장에서 티켓 받을 건데 준비할 게 뭐야?

기대 결과:

- 일반예매 일정
- 현장수령 관련 정보
- 본인확인 관련 정보
- 필요한 준비물
- 팬클럽 선예매와 무관한 정보 최소화

### Test 3. 배송 + 취소

입력:

> 티켓 배송은 언제 시작하고 취소는 언제까지 할 수 있어?

기대 결과:

- 티켓 배송 일정
- 취소 가능 기간
- 취소 수수료 또는 관련 규정

## 12. 비기능 요구사항

### NFR-001. 응답 근거성

예매 일정 및 정책과 관련된 답변은 반드시 수집된 예매 공지를 기반으로 해야 한다.

### NFR-002. 환각 최소화

공지에서 확인되지 않는 정보를 생성하지 않는다.

### NFR-003. 응답 가독성

긴 문단 하나가 아니라 일정, 준비사항, 티켓 정보, 주의사항 등으로 구분하여 출력한다.

### NFR-004. 장애 격리

HTML 수집 또는 이미지 분석 중 일부 단계가 실패하더라도 가능한 범위의 결과를 제공한다.

### NFR-005. 범위 제한

MVP에서는 높은 범용성보다 하나의 NOL Ticket 공연 페이지를 안정적으로 분석하는 것을 우선한다.

## 13. LangChain 활용 요구사항

본 프로젝트에서는 최소 다음 LangChain 구성 요소를 활용한다.

1. **Document Loader**  
   예매 페이지의 HTML 텍스트를 LangChain Document로 변환한다.

2. **Text Splitter**  
   긴 예매 공지를 검색 가능한 Chunk로 분리한다.

3. **Embedding**  
   Document Chunk를 의미 기반 검색이 가능한 벡터로 변환한다.

4. **Vector Store**  
   Embedding된 Document를 저장한다.

5. **Retriever**  
   사용자 질문과 관련 있는 예매 공지를 검색한다.

6. **Prompt Template**  
   역할, 사용자 질문, 사용자 조건, 검색된 Context, 제약조건, 출력 형식을 일정한 구조로 LLM에 전달한다.

7. **Chain**  
   Document Ingestion, Query Understanding, RAG Answer 흐름을 단계별로 구성한다.

8. **Structured Output / Output Parser**  
   LLM 응답을 서비스에서 사용할 수 있는 일관된 데이터 구조로 변환한다.

## 15. 완료 조건

다음 조건을 모두 만족하면 MVP 구현 완료로 판단한다.

- NOL Ticket 상품 URL을 입력할 수 있다.
- HTML 형태의 예매 정보를 가져올 수 있다.
- 상세 이미지에 포함된 공지 텍스트를 추출할 수 있다.
- HTML과 이미지 데이터를 LangChain Document로 관리할 수 있다.
- Document를 Chunk로 나누고 Vector Store에 저장할 수 있다.
- 사용자 질문에 따라 Retriever가 관련 Chunk를 검색한다.
- 질문 분석 결과를 Retrieval에 활용할 수 있다.
- 검색된 Context를 기반으로 LLM이 답변한다.
- 결과를 일정 / 준비사항 / 티켓 정보 / 주의사항 / 근거로 구조화한다.
- 공지에 존재하지 않는 내용을 임의로 생성하지 않는다.
- 서로 다른 질문 최소 3개에서 서로 다른 관련 Context와 답변이 반환된다.
- HTML 또는 이미지 분석 일부가 실패했을 때 전체 서비스가 중단되지 않는다.

## 16. 핵심 원칙

이 프로젝트의 핵심은 **예매 페이지 전체를 단순 요약하는 것**이 아니다.

~~~text
사용자의 자연어 상황 이해
        +
관련 공지 검색
        ↓
필요한 Context만 구성
        ↓
개인에게 필요한 예매 정보 제공
~~~

같은 공연 페이지라도 사용자의 질문과 조건에 따라 Retriever가 선택하는 Context와 최종 답변이 달라져야 한다.
